# Miloco production runtime diagnosis progress

## 2026-08-29 18:38 SGT

- Current work: Completed read-only production diagnosis on `docker.esxi` under CO `CHG260829004` for RTSP perception-device visibility, browser live video, and Omni model rejection. No configuration, container, image, database, Xiaomi account, camera source, or credential was changed.
- Expected result: Identify the first failing boundary for all three symptoms without exposing RTSP credentials, the Miloco service token, or the model API key, then prepare a bounded repair design for user approval.
- Result: Achieved.
  - Runtime baseline: exact deployed SHA `5fd053e620636c32dd0f7c439d25bd40a743d965`, image `miloco:5fd053e620636c32dd0f7c439d25bd40a743d965`, container healthy. Two enabled RTSP sources were connected with H.264 video and were returned by both `/api/cameras` and `/api/perception/devices`; the perception engine reported both as active sources. The dashboard still showed `0 个在感知` because its perception cards/count are built only from MIoT `scopeCameras`, while RTSP sources are rendered in a separate management section.
  - Browser live view: both WebSockets authenticated and emitted H.264 Annex-B data. Each source delivered SPS, PPS, SEI, and IDR NAL units in its first key access unit, and Chrome reported support for `avc1.64001F`. On direct HTTP, `VideoDecoder` is unavailable and the page correctly selects MSE/JMuxer, but both `<video>` elements stayed at `readyState=0`, with no buffered range, dimensions, or playback. Source review identified a deterministic MSE readiness race: `ensureMseDecoder()` feeds the first access unit immediately after constructing JMuxer, while JMuxer v2.0.5 drops its init/media segments when `sourceopen` has not yet set `mseReady`; its later `onReady` callback does not replay those dropped segments or create the missing buffer.
  - Omni model: the active profile was saved as `openai_chat_completions`, model `grok-4.6`, with a non-empty key. Its text-only preflight returned HTTP 200 in 4883 ms, while real perception calls sent video content to `/v1/chat/completions` and repeatedly returned HTTP 400, opening the configuration circuit after four failures. The same saved model, Base URL, and key passed the real image preflight through `openai_responses` with HTTP 200 in 7102 ms. The green connection test and red runtime banner therefore measure different payload capabilities; the key and model identifier were not the failing boundary.
- Next step: Present the repair approaches and recommended bounded design to the user. After approval, write the design specification and TDD implementation plan. Production repair will require a separate exact-SHA change CO; this diagnostic CO authorizes no mutation.
