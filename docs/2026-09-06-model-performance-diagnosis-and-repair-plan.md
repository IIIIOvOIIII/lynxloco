## 结论

当前实时识别的主要瓶颈是 Omni 阶段耗时与 4 秒输入窗口不匹配。与此同时，监控存在可复现的重复计数和统计单位混用，不能把页面 96.7% 直接解释成准确的视频丢失率或事件漏检率。Agent 为零有对应的无事件记录，尚无证据表明 Agent 通路持续失效。

推荐顺序：**校准指标与取帧 → 测量当前 Grok 端点并发容量 → 实现有界跨窗口模型并发 → 验收窗口覆盖和事件漏检 → 容量不足时再优化负载或更换端点**。

2026-09-06 用户补充目标：优先在当前模型处理效率基础上增加同时送模的能力，以减少未处理窗口造成的漏检。本计划据此将并发从后续可选项提升为主修复路线。架构上可实现；生产吞吐能否随并发提高仍需实测。此修订使用同日已保存的生产证据和当前源码，没有重新访问生产或进行负载测试。

## 已确认的问题

### 1. Omni 服务时间过长，消费者持续落后

`perception/runner.py` 按批次等待 `process_realtime()` 完成后才处理下一批。`perception/engine/pipeline.py` 已通过 `asyncio.gather` 并发处理不同摄像头，但整批仍需等最慢一路结束。因此，已有摄像头间并发不能消除跨批次等待。

4 秒输入对应平均约 39 秒成功处理，即忙碌阶段平均约 9.8 倍窗口时长；P95 约 20.8 倍。`max_windows=3` 只能缓存约 12 秒的 ready 窗口；长请求期间 `clear` 会反复清空缓存，随后 `drain_ready()` 又只取最新窗口并跳过较旧窗口。积压通过丢弃被释放，所以入队等待仅 1–4 秒并不代表系统跟得上输入。

资源检查：2 vCPU、约 5.8 GB 内存；Miloco RSS 约 3.4 GB，主机可用内存约 1.3 GB，根盘使用率 23%。短时 vmstat 的 CPU 空闲为 96–99%，无 swap-in/out；两次压力快照中 memory pressure 为零、I/O pressure 接近零。结合每批耗时分解，未发现当前主要瓶颈是持续 CPU、内存或磁盘饱和。

Identity 阶段在最近一小时成功批次中平均约 2.16 秒，属于模型提速后仍需考虑的次级开销；采集、转换、日志入库耗时远小于模型阶段。

### 2. `clear` 对同一个窗口重复计数

`perception/collect/stream_buffer.py` 中 `_windows` 已包含 ready 窗口，当前清空分支却使用：

```python
dropped = ready_before + active_before
```

本地在与生产一致的源码上构造 4 秒窗口、最多 3 个 ready 窗口的最小复现，结果如下：

```text
触发清空时：ready=4，_windows 中共有 5 个不同窗口
清空后：当前窗口被重建并保留
实际完全丢失：4 个不同的完整窗口
记录 dropped：9
```

生产最近一小时的有界日志样本包含 369 次同型记录：`clear, ready=4, active=5, max=3, dropped=9`。这是线上源码和本地行为共同支持的计数缺陷。

当前窗口清空后可能丢失已有部分帧，应另记“部分窗口截断”，不能把它与被完全丢弃的历史完整窗口合并重复计算。历史记录没有保留完整窗口标识及所有截断细节，不应直接回填一个声称精确的历史真实丢失率。

### 3. 仪表盘混用了批次、摄像头窗口和并发时间

- `observability/aggregate.py` 把设备丢弃窗口数相加；`stats.summary()` 用它除以“设备丢弃窗口 + 批次数”。两路摄像头的一批通常消费两个窗口，这个分母单位不一致。
- `dropped_windows_total` 同时包含溢出清空和取最新窗口时主动跳过的窗口；“队列满整窗丢弃”的页面解释不完整。
- 同一聚合器把并发设备的 `omni_ms` 相加；它代表累计设备耗时，不代表批次墙钟时间。因此 Omni P95 高于端到端 P95 不足以说明计时先后异常。
- P95 的 `omni_error_count=0` 条件还包括 Gate 跳过、根本没调用 Omni 的批次。最近 24 小时 18,861 批次中 17,866 批被 Gate 跳过，页面端到端 P95 仅约 1.64；实际成功 Omni 批次的端到端 P95 约 25.09。不同分组混在一起会掩盖模型慢的问题。
- `perception/service.py` 的 runtime-summary 对增量丢弃计数使用 `MAX`，与仪表盘 `SUM` 不同，应在同一次指标修复中统一。
- `omni_call_count` 是批次级二值；当前多相机实现实际上可发多个请求。固定窗口内 79 个 Omni 尝试批次对应 86 个设备尝试，真实请求指标应另列。

### 4. 输入视频证据偏少，可能影响识别能力

固定一小时内：

| 摄像头 | 已处理窗口 | 零视频帧 | 仅一帧 | 两帧及以上 | 每窗平均视频帧 |
|---|---:|---:|---:|---:|---:|
| 客厅 | 91 | 51 | 32 | 8 | 0.63 |
| 厨房 | 65 | 4 | 53 | 8 | 1.14 |

这些是送入处理批次的设备窗口记录，不是网络摄像头的原始帧率，也不是已经核验的最终 HTTP 图片数。它们不足以支撑“每个 4 秒窗口都给模型 4 张有效连续画面”的假设。

已定位的检查点：RTSP 音视频共用容量 3 的 ingress 队列、3 fps 准入、128 MiB 视频帧保留上限、时间戳校准、clear 重建窗口及 latest-window 选择。以上可能共同影响留存帧，本轮尚未证明哪一处是零帧的直接主因。切勿据此直接断言摄像头掉线，或立即降低 Omni fps。

### 5. Agent 为零与未产生触发事件一致

最近一小时未发现 `suggestion`、`rule_match`、`interaction` 事件，`meaningful_events` 也是零；实际仍有普通感知描述入库。当前 `min_suggestion_urgency=low`，不存在由更高紧急级别阈值拦截全部建议的配置证据。

最近 6 小时有 1 次成功 suggestion Agent 调用；24 小时有 4 次成功调用，最近一次为 **2026-09-06 11:38:07 +08**，Agent 用时约 65 秒。当前数据库有 9 条启用规则。

Agent 仅在符合条件的规则/建议/语音交互事件上执行，不要求每次图像识别都调用。另须注意：发送失败、投递超时或缺少回传元数据可能不生成 `agent_runs` 行；所以这张表不是完整投递尝试日志。本轮最近一小时有界日志也未发现 dispatcher/webhook 条目，支持“该窗口未发生触发”，不能证明真实场景本应无事件。

## 修复路线比较

| 路线 | 适用条件 | 代价与取舍 |
|---|---|---|
| A：当前模型有界跨窗口并发（推荐） | 当前模型入口能同时服务多个请求 | 可减少因跳过窗口而漏掉事件的机会；单次识别仍可能等待几十秒，吞吐和费用需要测量 |
| B：跨相机隔离，每相机仍只有一个在途请求 | 希望先交付较小的调度改动 | 能减少相机间互相阻塞；单相机覆盖率仍受单请求耗时限制，仅作为过渡步骤 |
| C：保留测得的有效并发上限，精简负载或换端点 | 网关串行、共享算力饱和或并发没有有效吞吐收益 | 优先减少每次调用成本；若仍不足，再由用户决定是否接受较慢观察模式 |

本轮推荐 A。队列容量与同时执行的请求数是两个参数：扩大待处理队列只提供暂存；跨窗口模型并发才有可能增加每分钟真正完成的识别数。两者需配套修改，且必须取消当前无条件“取最新并跳过其余窗口”的消费方式在覆盖任务上的使用。

## 并发可行性与容量估算

当前代码已经支持同批不同摄像头并行 HTTP 等待，但批次之间串行。`InferenceWorker` 的持久事件循环可以承载多个等待网络的协程，因此不必简单增加相同数量的线程或复制多套本地模型。

以两路摄像头、每路每 4 秒一个窗口估算，持续有活动且所有窗口都需送模时，到达率为 `2/4 = 0.5 请求/秒 = 30 请求/分钟`。用 **40 秒/请求作为规划假设**：它来自已测成功批次约 39–41 秒的耗时量级，并非已测单个 HTTP 请求均值。实际容量试验必须重新测量包含失败、重试和并发影响的服务时间。

| 全局在途模型请求数 C | 假设服务时间不随并发变化，理论完成量 | 相对全部 30 窗口/分钟的理论容量 |
|---:|---:|---:|
| 2 | 3 请求/分钟 | 10% |
| 4 | 6 请求/分钟 | 20% |
| 8 | 12 请求/分钟 | 40% |
| 20 | 30 请求/分钟 | 100%，恰好满载，没有余量 |
| 25 | 37.5 请求/分钟 | 容量为到达量的 125%，满输入时利用率约 80% |

这张表是容量算术，不是实测覆盖率、漏检率或承诺。4–8 路有望产生实际增益，但不能据此声称覆盖全部连续窗口；20 路只是上述假设下的理论临界值，不是应立即设置的参数。25 路仅示范留余量的量级，首轮不测试超过 8 路。

通用容量关系为 `λ = N × p / W`、`理论吞吐 ≈ C / S(C)`，其中 p 是完整输入中确实需要送模的窗口比例，S(C) 是该并发档实际请求服务时间。稳定运行需要 `λ × S(C) < C`，并对长尾留余量。当前 Gate 比例来自已经大量丢弃后的已处理样本，不能直接作为 p。

并发改善的主要是窗口覆盖和排队等待，不会把每次约 40 秒的服务时间自动变成 4 秒。事件可被迟到识别，实时控制仍需满足自己的时效要求；报告必须分别展示“已识别但迟到”和“在时限内识别”。增大输入吞吐后 Gate/Identity 的 CPU 时间也可能成为新瓶颈，应在试验中一并测量。

交付标准：相同输入的每个完整摄像头窗口只属于一次处理、一次丢弃或仍在缓冲；跳过原因分明；图表数值与原始事件可一致重算。此阶段只证明指标可信，不声称推理提速。

### P1：测量实际模型请求，恢复视频输入质量

未来只读 CO 应明确覆盖 `miloco.esxi` 与模型网关 `ai.esxi`；当前 `CHG260906002` 只授权前者且已关闭。若需检查已存 Qwen 档案的服务主机，先核对它的真实主机身份并列入授权范围。

1. 关联 Miloco 和网关现有请求：只记录请求标识、起止时刻、状态、输入图片数量/尺寸/总字节、提示词长度、输出预算、实际 usage、响应文本长度和结构化解析结果。区分排队、上传、首字节等待和生成时间；不存在的计时项明确标为未测量。
2. 校验输出预算契约。当前默认请求预算为 512，但最近一小时供应方 usage 平均 output 约 1,773、最大 5,649，平均 input 约 12,036。该差异可能涉及网关预算处理或 usage/推理 token 口径；先查实际请求与实现，不能直接认定预算失效或据此算账单。
3. 按摄像头核对 decoded → ingress → admitted → retained → ready window → HTTP image 的数量及时间跨度。优先查客厅零帧和厨房单帧；为确认的丢帧点补最小修复，不凭共享队列存在就直接重写。
4. 保持内存上限，避免音频突发淘汰所有视频；如实测是该问题，再调整音视频保留策略。若是原尺寸 BGR 缓存过大，按识别需要降低保留尺寸并验证小目标质量。现有清晰度设置不应未经测量直接全面下调。
5. 检查最新帧时间与有效视频帧时间是否分开；音频持续到达不能成为“视频正常”的唯一依据。

交付标准：能够定位主要模型等待发生在哪层，解释零/单帧窗口的来源，并给出保持事件与人物/宠物识别质量的候选配置。

### P1：当前模型的并发容量试验

保留当前 `grok-4.6` 与输入负载，先回答上游是否提供真正的并行服务。读取已有网关记录可走只读 CO；向生产模型网关新增压力请求必须使用明确包含负载、并发、请求预算和停止条件的 Software CO，不能沿用只读权限。范围覆盖 `miloco.esxi`、`ai.esxi` 及实际会访问的模型主机。

1. 固定 24 个有标签的完整感知请求，涵盖两路相机、正例/负例和当前图片、规则、身份上下文负载；使用合成或明确允许的样本。各档使用同一组请求，关闭设备动作。
2. 按 `C=1 → 2 → 4 → 8` 分档测量，每档最多 24 次请求，总计最多 96 次、60 分钟。上一档已出现吞吐不增且耗时/错误恶化时，不继续更高档。记录同时存在的正常生产请求，不能把“新增测试并发数”冒充“端点总并发数”。
3. 分开记录送达、HTTP 完成、解析成功、语义正确、失败/429/超时；以每分钟语义有效完成量评估收益，同时记录服务时间和 token。对出现重试的请求连同重试占用一并计费、计时、计槽位。
4. 比较 C 与 S(C)：若并发翻倍而每请求耗时近似翻倍，真实服务量基本没增加，停止扩并发并进入后面的容量不足路线。仅 HTTP 连接数变多、返回 200 或队列更深都不构成收益。
5. 此轮结果用于选择候选档，不将少量样本的 P95 或正确率当成最终发布门禁。选出有实际收益且不过载的一档后，冻结参数，进入固定到达率的窗口回放和已知事件验收。

初始工程验证采用全局 `C=4`、每相机最多 2 个在途请求；它是受控试验起点，不代表生产已具备该容量。只有实测收益支持，才试 `C=8`、每相机最多 4 个；端点若只支持更低档，则按实测选择。

### P1：实现有界跨窗口模型并发

这一项替代上一版“每相机始终最多一个在途请求”的限制。跨相机单飞可作为过渡交付，但不能当成用户要求的并发扩容已完成。

**执行结构：** 按摄像头时序进行取帧、Gate 和必要的身份预处理 → 生成独立且不可变的窗口请求 → 公平分配全局模型请求槽位 → 收集独立结果 → 按事件时间处理身份、规则与 Agent 结果。

需要修改或扩展的责任边界：

- `perception/collect/stream_buffer.py`、`collect/collector.py`、`collect/camera_adapter.py`：覆盖任务按序提取窗口并放入有界待处理队列；只在明确超额、超龄或重复合并时丢弃，记录原因。保留预览/主动查询既有的 latest/peek 语义。
- `perception/runner.py`、`processor.py`、`client.py`、`inference_worker.py`：拆开窗口准备、模型等待和结果处理；HTTP 槽位限制真实在途请求数，而不是只限制批次数；同一相机允许多个不同窗口的模型请求同时在途。
- `perception/engine/api.py`、`pipeline.py`：Gate 前帧、音频尾段、跟踪帧序按摄像头/源代际顺序更新。保留必要的串行预处理，不能把整个 `process_realtime()` 原样并发多开。
- `perception/engine/identity/dispatcher.py`、`identity/engine.py`、`omni/omni.py`：当前 `FusedDispatcher` 只有一个 `_pending`，`take_pending()` 不清空，响应通过共享 pending 回写；它不支持同相机多窗口并发。改为按 job 标识隔离候选、gallery、回调与失败清理，响应只作用于自己的请求；已在途窗口不依赖未来结果，同一 track 的身份确认按代际/帧序检查后回写。
- `perception/client.py`、`dispatch/dispatcher.py` 及规则处理边界：已有 early callback 会在完整结果之前派发事件，必须纳入统一的顺序和去重处理，不能绕过新调度直接触发旧事件。

队列策略与结果语义：

1. 每个任务持有相机、源代际、窗口起止时间、递增序号、请求配置版本和唯一 job 标识。请求结束、异常或取消均释放槽位；本地超时不代表供应方必定已经停止计费。
2. 工程试验初始等待队列上限为全局 8 个、每相机 4 个；与 C 独立配置。待处理和在途只保留必要的编码图片/音频及轻量上下文，不为每个 HTTP 请求复制一套 Identity/ONNX 引擎，也不长期保留整窗原尺寸 BGR。待处理加在途的编码 payload 总预算初始为 128 MiB，先实测单任务大小，空间不足时显式拒绝并计数，不能悄悄突破主机内存预算。
3. 公平轮转防止一路相机占满所有槽位；同一相机待处理窗口保持时序。容量不足时优先丢弃过龄窗口、可证明重复的静态候选，再按已声明优先级淘汰低优先级旧窗口；首次出现或变化较大的候选优先保留，但仍须统计未分析窗口，不能保证其中没有事件。
4. 首轮离线回放采用 120 秒事件年龄作为覆盖统计观察范围；这是实验窗口，不是生产控制指令的有效期。生产的最大等待年龄、结果等待缺口和各类动作有效期在回放后单独冻结，用户未批准前不将迟到历史结果直接送去控制设备。
5. 乱序结果按每相机窗口序号进入有界重排区。前序请求失败或到达截止时间，写明确缺口再推进，不能无限等它；超时不得当成“无人/未命中”更新状态。过了推进位置才返回的结果只归入历史证据，不回滚当前人员/规则状态、不重复派发动作。
6. 身份状态和语音续接确实依赖前序结果时，允许该局部依赖保持串行；其他可由窗口快照判断的画面/规则继续并发。对“历史识别覆盖”与“可安全用于实时动作的结果”分别验收，不能以提高吞吐为由破坏现有身份判断。

验证覆盖实际并发风险：同一相机 A/B 窗口反序返回、前窗超时后迟到、源重连改变代际、fused pending 不串窗、早送与最终结果不重复、规则进入/退出不倒序、停止/重启后旧任务不写回、队列/字节/请求槽位有界。复用 `tests/perception/test_inference_worker.py`、`tests/perception/engine/test_pipeline.py`、`tests/test_perception_client.py`、`tests/dispatch/test_dispatcher.py`、现有 identity/fused 测试，并增加同相机跨窗口调度的集成用例。

交付标准：证明同相机确实有两个以上模型请求重叠；快相机不必等慢相机整批结束；在同一条固定到达率回放上，语义有效窗口完成数和已知事件召回提高，同时报告端到端年龄、误报、真实模型请求量和费用。指标正确性、零帧问题与乱序状态正确性仍是前提。

### 条件分支：并发容量不足时的模型与输入参数实验

只有当前端点的并发试验无法获得足够有效吞吐时，才优先进入本节；不把更换模型设为开展跨窗口并发的前置条件。

1. 先在本地或授权实验环境使用合成/明确允许的样本，设备动作关闭。模型调用属于下一阶段范围，本轮没有发送样本。
2. 首轮至多 12 次请求、20 分钟：当前 Grok 和已保存的 `qwen3.5:4b-mlx` 档案各测 2 种固定负载、3 个相同样本。Qwen 档案存在不代表已通过真实视觉或结构化识别验收；先通过多种已知图像与结构契约检查。
3. 两种负载分别为生产形状基线和经过取帧核验的精简负载。一次只改变一个变量；所有样本记录语义答案是否正确、事件字段是否完整及请求耗时。12 次仅用于可行性筛选和方向判断，不能将少样本 P95 或投票结果当成发布门禁。
4. 根据实测确定运行目标。若保留 4 秒连续输入，要证明长期服务能力覆盖通过 Gate 的请求到达率，且输出延迟满足事件持续时间；若做不到，明确选择模型/硬件/调度优化，或由用户接受较低时效的业务模式。
5. 候选方案再进入预先固定的 40 个标注窗口验收：静态、人物进出、宠物、目标规则事件各 10 个，包含正例和负例。同步报告漏检、误报、延迟、图片数、token、每个正确事件成本；人工核对的语义标签才是识别质量真值。

停止条件：同类失败最多两次恢复；错误/限流加重、成本达到预算或取帧证据不完整即停。预算是上限，足够得出结论时提前结束。不能只以 HTTP 200、存在 output_text 或模型名称正确为验收。

若所有候选都不能支撑完整输入，保留实测最有效并发和有界队列，按时间段/活动变化做覆盖采样并明确未处理区间；不得只堆积历史窗口直到结果不可用。调整采样周期须使用实测 `W > N × p × S(C) / C` 并留余量，同时检验短事件召回。接受更低时效属于产品目标变更，需要用户明确选择。

### P2：验证从已知事件到 Agent 的完整链路

涉及 `perception/client.py`、`dispatch/dispatcher.py`、`observability/agent_meta_poller.py` 和相应测试。

以合成或标注的已知正例追踪：有效画面 → Gate → 模型解析 → 规则/建议 → 去重/阈值 → 入队 → 发送 → Agent 回传。分别统计投递尝试、成功、失败、超时、等待元数据和没有触发条件。

先用测试适配器验证“应触发时恰好触发，静态负例不触发”，再用固定 40 个标注窗口（静态、人物进出、宠物、目标规则事件各 10 个，包含正例/负例）比较原调度与候选并发调度。按原始时间间隔回放，统计同一事件是否至少识别一次、是否及时、是否误报；不得用丢弃窗口比例直接替代事件漏检率。之后的生产验收必须在单独写入 CO 中明确模型请求、目标事件、Agent 行为及设备动作范围。不能为了让数字大于零而触发真实设备动作。

## 发布、回滚与复查

每阶段保留独立变更和验证证据；代码完成后按仓库流程提交、推送，通过发布检查，再创建绑定精确 SHA 的 Software CO。用现有 `deploy.sh` 与 Miloco/OpenClaw 生产部署路径，禁止临时复制整套工作区替代发布流程。

配置实验要记录已批准字段的前值，代码发布保留可用回退版本；SQLite 结构更改采用向后兼容方式，回滚不删除历史记录。并发调度默认关闭，按测定档位逐级启用；切换或回滚前停止新任务入队，有界等待在途任务结束，切换源代际并忽略旧响应，再恢复旧调度，避免两个模式同时派发。发布后至少观察一次固定 30 分钟两相机负载，同时读正确口径的窗口覆盖、成功 Omni 延迟、错误类型、实际帧数、已知事件召回与 token 开销。验收目标在前述可行性测量后冻结，运行中不改规则。

## 审查结论与限制

- **完整性：** 生产版本与相关源码一致；数字来自只读 SQLite 和有界日志；计数缺陷在本地复现；固定窗口证据可离线核对。终态 health 200，进程未重启，配置 mtime 未变。
- **目标适配：** 用户需要的是及时、正确的模型识别。仪表盘变绿、丢弃率降低或 Agent 次数变多都不单独代表目标完成。
- **成本：** 本轮未新增推理或 Agent 请求。供应方报告的 24 小时 realtime 使用量约 1,365 万 input tokens、230 万 output tokens，对应 5 条 meaningful events、4 次成功 Agent 调用；这只能说明需要评估每个正确事件的成本，不能把“无事件”一律视为浪费，也不能据 usage 推算未核实的实际账单。

尚未测量：模型网关内部排队/供应商真实耗时、摄像头完整原始媒体帧率、在线最新诊断 API、真实事件识别准确率。本轮 Vault catalog 未找到可用于 Miloco 服务 API 的具体 token ref，因此没有绕过 Vault 从配置取 token 调用受保护 API。已用授权范围内的数据库、日志和源代码完成本次诊断；下一阶段如果需要受保护 API，先补充或确认正确 ref。

过去发生过的模型/端点问题仅用于定位调查入口，本报告当前状态均以本次现场证据为准。
