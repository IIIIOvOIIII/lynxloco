## 当前瓶颈及证据

### 1. 8 路能提高处理量，但慢请求仍超过有效时限

8 路实际峰值达到 8，成功处理量约为旧吞吐参考的 5.6 倍。成功请求 HTTP 耗时中位数 38.8 秒、P95 84.4 秒，成功窗口整体处理 P95 115.4 秒。52 个失败窗口中，HTTP 已执行时间中位数达 111.4 秒，窗口总耗时中位数 119.7 秒；失败类型均为 `CancelledError`，网关对应 `request_canceled/499`。

这证明串行限制被解除后仍存在模型长尾耗时，不能承诺简单增加并发就消除遗漏。客厅有视频的 72 次请求中有 44 次失败，占 8 路所有失败的主要部分；厨房有视频的 88 次中有 7 次失败。应继续定位客厅的实际负载与取帧链路，不能直接归因于摄像头硬件。

### 2. 4 路加重等待，现有等待容量不适合当前模型耗时

4 路实际峰值达到 4。失败窗口等待模型名额的中位数 **57.6 秒**、P95 **106.1 秒**；成功窗口的等待中位数也有 **36.5 秒**。失败窗口总处理时间中位数约 119.6 秒，显示等待与模型执行一起耗尽 120 秒窗口年龄预算。

两档的成功网关请求平均耗时接近：8 路约 38.3 秒，4 路约 37.6 秒。降低并发没有让同类成功请求明显提速，却增加了等待压力。自然观察的活动、帧数与输入 token 不同，因此这不是严格同负载的因果试验；等待耗时本身则是实际计时证据。

### 3. 推理负担与视频输入仍需分别优化

网关对应版本为 `v3.1.5-amd64`，OCI 标签源码版本 `88ef5bd948001924a8f71c9e8ac8b8dfacace5b0`，实际路由 `grok_build / Build/grok-4.6`。Miloco 未明确指定推理强度。8 路成功请求平均输出约 1,894 token，其中推理约 1,811（约 95.6%）；4 路约 1,803，其中推理约 1,715。

核对[对应版本的请求归一化代码](https://github.com/chenyme/grok2api/blob/88ef5bd948001924a8f71c9e8ac8b8dfacace5b0/backend/internal/infra/provider/cli/normalize.go)，未指定推理强度时不会补入一个明确 effort；原有输出预算字段被保留。[该版本模型能力定义](https://github.com/chenyme/grok2api/blob/88ef5bd948001924a8f71c9e8ac8b8dfacace5b0/backend/internal/domain/model/reasoning.go)支持 Grok4.6 的 low/medium/high/xhigh，可将 low 纳入下一轮单变量试验。本轮没有改变推理强度；供应方是否按预期执行输出预算仍未实测，不能声称已定位为“网关丢失预算”。

8 路客厅 163 个处理窗口中 88 个零视频，厨房 235 个中 35 个；4 路对应 14/89 和 6/175。源活动明显不同，不能据此认定仅降档就修好了取帧。还要区分合法的语音/文本窗口与应有视频却缺帧的窗口。

主机在两档结束时均健康 200，后端 RSS 分别约 1,673 MB、1,433 MB，可用内存约 2,958 MB、3,168 MB，内存压力快照为零。实际限流日志达到配置峰值，未发现超出上限；编码负载峰值记录为启动爬升时约 15.7 MB/11.5 MB，不能当作整个区间的连续最大值。

### 4. Agent 通路有一次真实成功证据

8 路没有 suggestion/rule/interaction 触发事件及 Agent 完成记录。4 路自然出现 1 条 suggestion、1 条 rule_match，并有 **1 次成功 suggestion Agent 完成回传**。本轮没有人为触发真实设备动作。这证明一次事件到 Agent 回传通路可用，不证明所有规则投递或物理设备动作均已验收，也不证明真实家庭事件召回率。

## 下一轮修复顺序

1. **先改等待准入，保留并发能力。** 将在途并发与等待容量分开处理。根据窗口剩余年龄和实测模型服务时间限制等待；在剩余时间明显不足时于 HTTP 前过期，减少已无法及时完成的请求。用代表性回放选出较小等待容量和最大等待时间，不能在 4/8 档都机械保留同样深的等待队列。所有拒绝/过期仍计入未处理覆盖，不能靠改分母改善指标；保留结果排序与 120 秒年龄边界。
2. **单独验证 Grok 推理负担。** 在相同的完整视觉、身份、规则负载上比较当前默认与明确 low，观察 JSON 完整性、人物/宠物/规则正确性、耗时及实际 usage。先校验输出预算契约，不同时更换端点或全面降低画质。
3. **定位客厅输入与负载。** 只记录解码→入队→留存→窗口→最终图片的数量、时间跨度和字节等元数据，解释零帧与慢请求集中原因。保留合法语音处理，不把所有零视频窗口简单过滤掉。
4. **补齐已知事件验收。** 使用有标签的静态、人物进出、宠物、目标规则正负例，关闭真实设备动作，用测试 Agent 适配器验证应触发时恰好触发。分别计算漏检、误报、及时识别和每个有效事件的请求量，不能用窗口丢弃率替代召回率。
5. **重新冻结有限预算后发布。** 本轮 80 次额外请求和两段 30 分钟观察已经用完。后续先完成本地代表性验证，再以新源码 SHA、新 CO 和明确的新调用预算执行；不追加第三档或反复重跑寻找通过结果。
